## 1. 本轮范围和明确取舍

### 1.1 需要重点修改的三条主线

本轮重点对应原审查结论中的第 4、5、6 项：

1. 建立除通道范围外的统一输入和节点数据校验，避免非法物理量、层号、时间或节点图
   被编译成可执行 FPGA 帧；
2. 重构 `EngineCtrl`、API 回调和 `USEEngine` 的异常边界，保证启动、运行、停止任一
   阶段失败时都能先关闭功放并释放控制状态；
3. 让 AutoCal 与普通实验、更新流程互斥，统一 FPGA 串口和 ACK 的所有权。

同时纳入不会改变实验算法的运行可靠性优化，例如串口就绪、核心任务监督、DO 任务
隔离、保护 fail-closed、标定文件事务、进程退出清理和更新目录事务。

### 1.2 本轮不处理

按当前设备基本离线、内部使用的部署条件，下列问题不进入本轮修改范围：

| 暂不处理项 | 本轮处理方式 |
|---|---|
| WebSocket 认证、授权、TLS、Origin 和监听地址 | 不修改 |
| OTA HTTP、发布签名和软件包来源真实性 | 不修改 |
| `ApiScanTest` 的实验算法、DI 报告和正反扫问题 | 不修改 |
| `MapChannel()` 和前端通道 `0..11` 范围校验 | 继续由前端保证 |

这里的“不处理”表示不列入当前代码任务，不影响以后部署条件变化时重新评估。

### 1.3 保留节点的处理决定

节点 `0x0000` 和 `0xFFFF` 本轮首先通过项目执行文档和 API 编写规范重点约束，不把它
并入第 4 项通用输入改造：

> API 可以把 `0xFFFF` 用作 `diMatchId`、`timeoutId`、`countOverId` 或停止触发目标，
> 但绝对不能把 `0x0000` 或 `0xFFFF` 作为 `upsertNodes()` 的 key。

- `0x0000` 是系统初始化锚点：FPGA reset、0 V/50 Hz、SYS_START 和 DI 防抖；
- `0xFFFF` 是系统终止锚点：FPGA reset、DO=0 和控制层结束通知；
- 可写实验节点范围为 `0x0001..0xFFFE`；
- API 代码评审必须逐项检查所有 `upsertNodes()` 字典；
- “禁止写入”与“允许跳转到保留节点”必须在所有 API 文档中明确区分。

## 3. M-01：输入与 `ApiNodeData` 数据契约

### 3.1 校验边界

建议建立两层校验：

```text
前端物理量
  -> BaseApi 物理域校验
  -> physDictToReg()
  -> ApiNodeData 寄存器域校验
  -> EngineCtrl 临时编译
  -> 完整节点图校验
  -> 一次性提交给 USEEngine
```

本轮不增加 `MapChannel()`/API 通道范围校验，其余校验不能依赖前端。

### 3.2 物理域校验

在调用 `Calibration.PhysToReg()` 前检查：

- 每个通道下的层对象必须是字典；
- 层号只能为整数 `0..64`；
- 每层必须恰好包含 `[amplitude, freqOrPhase]` 两个数；
- 两个数必须是有限值，拒绝 `NaN`、`+Inf`、`-Inf`、布尔值和字符串；
- layer 0 的第二项按频率范围检查；
- layer 1..64 的第二项按相位接口约定处理；
- 幅值按产品配置的电压、电流和校准后安全范围检查；
- `steps` 按增量校验，并检查每个累计前缀，不只检查单步；
- RMS/峰值的接口约定必须在进入转换前统一，不能由不同 API 隐式猜测。

物理上限建议放入单独设备配置，例如：

```python
OutputLimits(
    voltage_peak_max=...,
    current_peak_max=...,
    frequency_min=...,
    frequency_max=...,
    max_test_duration_ms=...,
)
```

具体值由硬件和产品定义确认，校验代码不要散落在各 API 中。

### 3.3 编码函数

`FPGACodec.ConvertAmpToReg()`、`ConvertFreqToReg()` 和 `ConvertDbncToReg()` 当前主要依靠
位掩码得到目标宽度。修改为：

1. 先检查数值类型和 finite；
2. 计算未截断整数；
3. 检查是否落在目标寄存器和产品允许范围；
4. 超界抛出明确的校验异常；
5. 最后才转换为 U32/U8 表示。

DI 防抖 U8 的无绕回上限约为 `83.5584 ms`。超过范围应明确拒绝或按产品配置钳位，
不能通过 `& 0xFF` 变成更短时间。建议选择“拒绝并回前端错误”，便于发现配置问题。

### 3.4 `ApiNodeData` 结构校验

通用校验矩阵：

| 字段 | 校验内容 |
|---|---|
| `mode` | 只接受当前明确启用的 mode |
| `base/reset` | 字典结构完整；层 0..64；每项两个合法 U32 |
| `steps` | 列表结构；每步字典合法；单节点步数和总帧数有限 |
| `interval` | Mode2/3 必填；正有限毫秒数；有工程上限 |
| `resetTime` | Mode3 必填；非负有限毫秒数 |
| `resetDo` | Mode3 必填；只使用低 16 位 |
| `doActions` | 每项只使用低24位；延时升序；DO只使用低8位 |
| `timeoutMs` | 有 timeout 时必须同时提供 `timeoutId` |
| `diMatchMask` | 低8位非零时必须同时提供 `diMatchId` |
| `countOverId` | 非空时必须是有效节点目标 |
| `gate` | Mode4 未开放前拒绝 |

模式组合：

| mode | 必要字段 | 禁止静默行为 |
|---:|---|---|
| 1 Static | `base` 可为空；按业务提供 DI/timeout/manual 出口 | 字段类型错误不得运行 |
| 2 Sweep | 非空 `steps`、正 `interval` | 空 steps 不得退化为 Static |
| 3 Reset | Mode2 字段 + `reset/resetTime/resetDo` | 缺字段不得退化或运行时异常 |
| 4 DcComp | 当前调度未启用 | 入口直接返回“功能未启用” |

### 3.5 节点图与遥测前置条件

一次上传前检查完整图：

- 所有 `countOverId`、`diMatchId`、`timeoutId` 都指向本次节点、已有节点或允许的系统
  目标；
- step 涉及的每个 channel/layer 必须能从本节点 base 或明确前驱状态确定；
- 所有可能路径都有业务规定的结束方式或最大运行时间；
- 单实验节点数、step 数、编译帧数和预计总时长不超过配置上限；
- 先在临时字典中全部编译成功，再同时更新 `EngineCtrl.nodes` 和 `USEEngine.nodes`；
- 任一节点编译失败时不保留半提交的 `self.nodes`。

### 3.6 错误返回

定义统一异常，例如：

```python
class ExperimentValidationError(Exception):
    code: str
    path: str
    message: str
```

前端错误至少包含 module、字段路径和原因：

```json
{
  "type": "error",
  "code": "INVALID_LAYER",
  "path": "params.statics.6.65",
  "msg": "layer must be in 0..64"
}
```

校验失败发生在启功放之前，不进入 Node 0 后续实验阶段。

## 4. M-02：EngineCtrl 事务化生命周期

### 4.1 建议状态

用显式状态替代单一 `running` 布尔值：

```text
IDLE
  -> PREPARING
  -> ZEROING
  -> RUNNING
  -> STOPPING
  -> IDLE

任意状态异常 -> FAULT -> STOPPING -> IDLE
```

状态变化统一在 `_startLock`/session 锁下进行。

### 4.2 两阶段 API 启动

当前 API 的 `setup()` 同时解析参数、创建后台任务、上传节点和触发节点，不便在启功放
前完成验证。建议拆为：

```python
prepared = api.prepare(ctrl, params)   # 纯解析、计算和节点构造
await ctrl.commit(prepared)            # 上传并启动
```

`prepare()` 不允许：

- 开功放；
- 发送 FPGA 帧；
- 启动不会被控制器追踪的后台任务；
- 触发节点；
- 向前端提前发送“运行中”。

迁移旧 API 时可先增加 staging 模式：`upsertNodes()` 在 PREPARING 阶段只编译到临时区，
`trigNode()` 只记录首节点；所有 API 迁移后再收敛成明确的 `prepare()` 返回对象。

### 4.3 新启动顺序

```text
获取 start/session 锁
  -> 保证功放关闭
  -> 等待或强制结束旧 session（有超时）
  -> 创建 API
  -> prepare + 全量校验 + 临时编译
  -> 确认 HWGateway 在线和 coreLoop 健康
  -> 提交节点
  -> 触发 Node 0
  -> 等待 Node 0 明确 tick/ACK（有超时）
  -> 确认零输出
  -> 启功放
  -> 触发 API 首节点
  -> RUNNING
```

Node 0 的完成事件应由 `EngineCtrl.onEvent()` 独立解析，不能再用固定 100 ms 代替硬件
确认。

### 4.4 回调异常边界

以下调用全部通过统一包装器执行：

```text
api.prepare/setup
api.onUpdate
api.onDi
api.onWebCommand
api.onStop
```

包装器策略：

1. 捕获并记录完整 traceback；
2. 保存面向用户的简短 `errorReason`；
3. 立即进入全局安全停止；
4. 报告失败不能阻止硬件停止；
5. 清理逻辑始终在 `finally` 执行。

`_doStop()` 的必要不变量：

```python
try:
    await_or_call_api_on_stop()
finally:
    activeApi = None
    running = False
    state.clear()
    nodes.clear()
    _stopEvent.set()
```

即使 `onStop()`、前端发送或寄存器反转换失败，`_stopEvent` 也必须释放。

### 4.5 停止顺序

```text
STOPPING
  -> 同步关闭功放 GPIO
  -> 设置不可被普通触发覆盖的终止意图
  -> DO=0
  -> 最佳努力发送 SYS_STOP / SYS_RESET
  -> 等待 FFFF 确认（有限超时）
  -> 调用 API onStop
  -> 清控制状态
  -> 发 error/report/stop
  -> IDLE
```

关闭功放是独立于串口、API 和前端的第一动作。FPGA 或 WebSocket 出错不能阻止这一步。

旧实验结束等待必须有超时；超时后走独立安全路径，不能让下一条 start 永久卡住。

## 5. M-03/M-04：USEEngine 与 HWGateway 存活管理

### 5.1 保存并监督核心任务

`USEEngine.start()` 应保存：

```python
self._core_task = loop.create_task(self.coreLoop())
self._core_task.add_done_callback(...)
```

`coreLoop()` 增加顶层 `try/except/finally`：

- 正常取消：执行安全清理；
- ACK timeout、帧构造、时间字段或其他异常：产生统一 `ENGINE_FATAL`；
- fatal 事件通过 EngineBridge 送回主循环；
- 主循环立即关功放并进入 FAULT/STOPPING；
- 不允许控制器在核心任务已经完成时继续接受 start。

### 5.2 硬件就绪

当前线程中的 `ready` 只代表对象已经创建。改成至少两个状态：

```text
thread_ready     硬件线程和 event loop 已创建
gateway_ready    UART 已连接且读写任务存活
```

EngineCtrl 开始实验前检查：

- `HWGateway.writer` 可用；
- UART reader task 存活；
- USEEngine core task 存活；
- 最近一次通信状态不是 fatal。

### 5.3 断线恢复

`HWGateway` 增加连接状态机：

```text
DISCONNECTED -> CONNECTING -> ONLINE -> BACKOFF -> CONNECTING
```

- 连接失败按有限退避重试；
- EOF/`IncompleteReadError` 后关闭旧 writer，不进入紧循环；
- 运行中断线立即通知控制器安全停止；
- 重连成功后先 FPGA reset 和 Node 0 初始化，不能直接恢复旧实验；
- `WriteBytes()` 在离线时返回明确错误，不对 `None` writer 调用。

### 5.4 ACK 错误语义

`flush()` 返回负时间戳后，当前运行函数不能继续下发普通波形帧。统一规则：

```text
ACK timeout / status FFFF / UART断线
  -> ENGINE_FATAL
  -> 除 STOP/RESET/DO0 外停止发送
  -> 主循环关闭功放
```

重建 session 时同时重置 `sentCount`、`ackCounter` 和历史 ACK 状态。

## 6. M-05：AutoCal 与硬件 session 互斥

### 6.1 唯一硬件所有权

增加共享 session 管理器：

```text
NONE
EXPERIMENT
AUTOCAL
UPDATE
SHUTDOWN
```

同一时刻只能有一个 owner：

- 实验运行时拒绝 `autoCal start/verify`；
- AutoCal 运行时拒绝实验 start；
- 任一输出 session 活跃时，更新/回滚先请求全局安全停止；
- owner 释放前必须功放关闭、DO0、FPGA reset；
- WebSocket 断开或保护动作调用全局 stop，而不是只停止普通实验。

### 6.2 统一串口和 ACK

AutoCal 当前通过 `EngineBridge.sendBytes()` 直接下发帧。修改方向二选一：

1. 推荐：AutoCal 使用与 USEEngine 相同的 `HardwareCommandArbiter`，每帧进入统一发送、
   ACK 和错误处理；
2. 过渡：进入 AutoCal session 时完整停止 USEEngine、清 ACK 计数；AutoCal 使用独立
   ACK waiter；退出时重新 reset 并启动 USEEngine。

不能继续让 AutoCal 帧产生的 ACK 只增加 `ackCounter` 而不增加 `sentCount`。

### 6.3 DMM I/O

PyVISA 的 `query/write` 和 `time.sleep()` 不在主 asyncio 事件循环直接执行。可使用：

```python
await asyncio.to_thread(dmm.query, ":READ?")
await asyncio.to_thread(dmm.write, cmd)
await asyncio.sleep(0.5)
```

所有操作有超时和停止检查。停止请求不等待一个完整 DMM 5 秒超时后才响应。

### 6.4 清理顺序

AutoCal 的最外层保证：

```python
try:
    await calibration_or_verify()
finally:
    try:
        setAmplifier(False)       # 第一优先级，独立 try
    finally:
        try:
            resetFpga()
        finally:
            close_or_idle_dmm()
            release_session()
            running = False
            stop_flag = False
```

即使 RESET 抛异常，也不能跳过关功放。

### 6.5 标定文件

保存步骤：

1. 读取旧配置；
2. 在内存构造完整新配置；
3. 校验所有现有项和新项；
4. 写同目录临时文件；
5. flush + fsync；
6. 重新读取并校验；
7. `os.replace()` 原子替换；
8. fsync 目录；
9. 立即 `calib.LoadCalib()`；
10. 失败时继续使用旧内存系数并向前端返回错误。

## 7. M-06：HWProtect 和全局急停

### 7.1 初始化必须 fail-closed

功放 GPIO、蜂鸣 GPIO 和硬件故障输入分步创建到临时变量；全部成功后再提交为
“保护健康”。任一必要 GPIO 初始化失败：

```text
protectionHealthy = False
amplifier = OFF
EngineCtrl.startTest() 返回硬件保护不可用
```

蜂鸣器可以定义为非关键设备；其失败只禁用蜂鸣，不能中断关闭功放或 stopTest。

### 7.2 全局 emergency stop

提供一个幂等接口：

```python
async def emergencyStop(reason, source):
    ...
```

可由以下来源调用：

- 硬件故障 GPIO；
- 虚拟热模型；
- UART/coreLoop fatal；
- API 回调异常；
- AutoCal stop/异常；
- WebSocket 活动连接断开；
- SIGTERM/SIGINT；
- 更新或回滚前置停机。

重复调用必须安全，普通节点触发不能覆盖已经登记的 emergency stop。

## 8. M-07/M-08：USEEngine 零散可靠性修改

### 8.1 DO 任务归属

进入任意新节点时：

1. 无条件取消旧 `_doTask`；
2. 等待取消完成；
3. 增加 `nodeGeneration`；
4. 每个延时 DO 写入前检查 generation；
5. 终止节点先同步写 DO0；
6. 不使用会让已取消写操作继续执行的无归属 `shield(setDo())`。

这样旧节点的延时动作不会在新节点中继续执行。

### 8.2 手动触发

把单个 `trigTarget` 改成带优先级的触发结构：

```text
EMERGENCY_STOP / FFFF   最高，设置后不可被普通目标覆盖
FAULT
MANUAL_NODE
```

写入触发时同时唤醒 `triggerEvent`，避免仅依赖最多约 25 ms 的轮询。

### 8.3 定时等待

移除硬件 UART event loop 中最后约 2 ms 的纯忙等。可选方案：

- 把精确定时交给 FPGA；
- 使用专用实时线程/定时器；
- 允许 asyncio 唤醒误差，但在发送下一 UPDATE 前先处理已经到达的 DI；
- 用硬件时间戳校正报告，不阻塞串口 reader。

Mode3 的 reset 窗口是否屏蔽 DI/timeout 保持现有产品语义，但要在文档和事件中明确
标记 reset enter/exit。

### 8.4 U32 时间戳

对 FPGA 时间戳做模 2³² 运算：

```python
adjusted = (timestamp - debounce_us) & 0xFFFFFFFF
delta = (end - start) & 0xFFFFFFFF
```

避免约 71.6 分钟回绕点出现负时间。

### 8.5 模式显式性

- Mode2/3 字段不足时返回校验错误，不静默转 Static；
- Mode3 的普通 `doActions` 要么实现，要么在 schema 中拒绝；
- Mode4 在调度恢复和真机通过前明确返回“未启用”；
- 将 `sleepForever()` 更名为表达“约 100000 秒上限”的名称，或真正实现明确的
  indefinite wait + 全局最大实验时长。

## 9. M-09/M-10：Calibration 和遥测热模型

### 9.1 Calibration 全量加载

`Calibration.LoadCalib()` 先在临时变量解析完整 JSON：

- key 能转物理通道；
- 每项恰好三个有限数；
- factor 不为 0；
- 通道集合满足设备要求；
- DC/AC factor 和 bias 落在校准工程范围。

全部通过后一次性替换内存数组。失败时不允许形成“部分通道新值、部分通道旧值”的
混合状态。

默认系数的 DC/AC 符号必须与实际硬件极性和 AC 相位补偿一致；最终值由真机校准定义。

### 9.2 reset 状态

Mode3 的 `tick=-1` 实际已经输出 reset，但 `EngineCtrl.state` 当前没有同步 reset。修改为
维护：

```text
activeState       当前 FPGA 理论 Active
baseState         当前累加 Base
phase             RESET / ACTION
```

HWProtect 始终读取当前 Active 理论值，而不是上一故障态。

### 9.3 AutoCal 热负载

AutoCal 直接寄存器输出也要向保护层报告：

```text
channel
DC/AC
amplitude register
start timestamp
stop timestamp
```

普通实验与校准共用同一个热模型入口。

## 10. M-11/M-12：进程和 WebSocket 运行可靠性

### 10.1 进程退出

`SysEngine.main()` 用 `try/finally` 和 signal handler 处理 SIGTERM/SIGINT：

```text
停止接收新命令
  -> emergencyStop
  -> 等待有限硬件确认
  -> 关闭 WebSocket server
  -> 关闭 UART writer
  -> 取消 reader/core/monitor task
  -> 停止硬件 event loop
  -> join 硬件线程
```

CPU affinity 同时捕获 `OSError`，记录告警后继续运行或按部署要求退出。

### 10.2 WebSocket connection generation

认证和网络安全不在本轮范围，但连接运行态竞态需要修复：

- 每个连接分配递增 generation；
- 先原子登记新 owner，再按明确策略关闭旧连接；
- 旧 Handler 的 finally 只有在 generation 仍是当前 owner 时才触发 stop；
- TX worker 发送失败时只有在 client/generation 仍匹配时才清 activeClient；
- 发送队列项携带 generation 或 session id；
- 新连接不继承旧连接尚未发送的实验控制消息。

### 10.3 消息归属

实验运行实例增加 `runId`：

```json
{
  "cmd": "next_node",
  "module": "status_sequence",
  "runId": "..."
}
```

普通 API 命令只交给 module/runId 都匹配的 active API。SysConfig、AutoCal 和实验消息
分别保留自己的 module，不由 `EngineCtrl._send()` 无条件覆盖。

后台发送 task 需要收集异常，并对高频 telemetry 做合并或限流。

## 11. M-13：Updater 和 SysConfig 本地可靠性

本节不修改 HTTP 或签名策略，只处理本地事务与进程稳定性。

### 11.1 互斥

update 和 rollback 使用同一进程级/文件级锁：

- 多个 update 互斥；
- update 与 rollback 互斥；
- 多个 rollback 互斥；
- 更新前通过 session manager 确认实验和 AutoCal 已安全停止；
- 锁跨 `SysConfig` 父进程和 `Updater.py` 子进程生效。

### 11.2 子进程读取

`SysConfig._runUpdater()` 同时消费 stdout/stderr，设置总超时：

```python
await asyncio.gather(read_stdout(), read_stderr(), wait_with_timeout())
```

超时后终止子进程并回传明确状态；非 JSON stdout 记录到诊断日志；stderr 设置大小上限。

### 11.3 解包

- 固定使用支持安全 filter 的 Python，或逐项检查规范化路径和链接；
- 不保留无过滤 `extractall()` fallback；
- 限制包下载大小、成员数量、单文件大小和解压后总大小；
- staging 完成后校验必须文件、产品、版本和可执行入口。

这里不改变软件包来源策略，只保证本地输入不会破坏 staging 之外的文件。

### 11.4 提交和恢复

当前“两次 rename”不是单一原子动作。建议：

```text
写 transaction journal
  -> fsync staging
  -> active -> backup/versioned
  -> staging -> active
  -> fsync parent directory
  -> 验证 active
  -> 标记 committed
```

服务启动时读取 journal，发现中断则自动选择完整的 active/backup 恢复。只有确认
systemd 重启请求成功且新目录完整后才回传最终 success。

### 11.5 USB/Wi-Fi 零散整理

- USB label 转安全 basename，并验证 mount 目录 realpath 仍在 `/media/pi`；
- 只有 mount 返回成功才记录成功；
- Wi-Fi 首次连接失败不要立即按 SSID 删除已有 profile；
- 清理 profile 时使用确认过的 UUID，并区分密码错误、瞬时失败和 profile 损坏。

## 12. M-14：其他代码整理

### 12.1 API Registry

- 动态扫描结果按确定顺序；
- 检测重复 `MODULE_KEY/MODULE_KEYS`；
- 单个模块 import 失败不影响其他 API；
- Registry 的显式列表作为可诊断 fallback；

### 12.2 日志

- RX 日志只记录 cmd/module/runId 和结构摘要；
- Wi-Fi 密码、校准口令等字段统一脱敏；
- 高频 ACK/DI/telemetry 使用采样或 DEBUG；
- 后台 task 异常全部进入统一日志和状态报告。

### 12.3 错误和类型

- `EngineCtrl.upsertNodes()` 返回结构化结果，不只返回 bool；
- API 必须检查 upsert/trig 结果后再推进内部状态；

- 禁止用宽泛 `except Exception: pass` 吞掉关功放、复位和文件保存错误。

## 15. 验收测试

### 15.1 输入和编译

- layer 0、1、64 分别编为 FF、00、3F；
- layer -1、65、256、257 被拒绝；
- NaN、Inf、字符串、缺少第二个值被拒绝；
- 超物理范围初值和任意累计 step 前缀越界被拒绝；
- Mode2 空 steps、Mode3 缺 resetTime/resetDo 被拒绝；
- Mode4 返回明确“未启用”；
- timeout/DI/countOver 悬空目标被拒绝；
- 编译中途失败不改变控制器和引擎现有节点。

按本轮决定，MapChannel/前端通道范围不在这些新增用例中。

### 15.2 保留节点文档约束

- API 编写模板明确可写 ID 为 1..FFFE；
- 所有正式 API 代码评审确认没有 `upsertNodes({0: ...})`；
- 所有正式 API 代码评审确认没有 `upsertNodes({0xFFFF: ...})`；
- `countOverId/diMatchId/timeoutId=0xFFFF` 仍作为正常终止示例；
- 文档说明跳到 0/FFFF 会清除普通节点。

### 15.3 生命周期

- 串口不存在时 start 被拒绝且功放保持关闭；
- writer 断线、ACK timeout、coreLoop 异常都触发 emergencyStop；
- API prepare/setup/onUpdate/onDi/onWebCommand/onStop 分别注入异常；
- 上述每种异常都在规定时间内关闭功放、DO0，并释放 `_stopEvent`；
- 旧实验不能终止时 start 在超时后退出，不永久等待；
- Node 0 未确认时绝不启功放；
- SIGTERM、systemctl restart 和 KeyboardInterrupt 都执行安全退出。

### 15.4 AutoCal

- 实验运行时启动 AutoCal 被拒绝；
- AutoCal 运行时启动实验被拒绝；
- 更新/回滚前能够停止并等待两者；
- AutoCal 的每个 FPGA 帧都有匹配 ACK；
- DMM 超时期间 stop 仍能在目标时间内关功放；
- RESET 抛异常时关功放仍执行；
- 校准保存中模拟掉电，旧配置仍完整；
- 保存成功后新系数立即用于普通实验；
- AutoCal 输出计入虚拟热模型。

### 15.5 DO、DI 与时间

- 跳节点后旧延时 DO 永不执行；
- 普通 trigger 不能覆盖已经登记的 FFFF emergency trigger；
- step 边界最后 2 ms 注入 DI 不会多执行一步；
- U32 时间戳在回绕点前后计算一致；
- Mode3 reset/action 切换时热模型读取当前实际理论状态。

### 15.6 WebSocket、Updater 和系统

- 旧连接发送失败不会清除新 active client；
- 旧 Handler finally 不会误停新 generation；
- 错误 module/runId 消息不推进当前实验；
- update/update、update/rollback、rollback/rollback 并发均被锁拒绝；
- 更新目录提交各故障点模拟掉电后能恢复；
- updater stderr 大量输出不造成父进程死锁；
- USB 卷标不能让挂载目录离开 `/media/pi`；
- GPIO 任一关键初始化失败时实验不可启动。

## 16. 完成标准

本轮优化完成的判定不是“正常实验还能运行”，而是同时满足：

```text
非法数据在启功放前被拒绝；
API 或引擎任一异常都先关闭功放；
实验、AutoCal、更新不争用 FPGA；
串口和核心任务状态对控制器可见；
停止请求不可被普通节点覆盖；
所有延时 DO 都属于明确节点 generation；
标定文件保存具有事务性且立即生效；
进程退出和更新前都进入确定的硬件安全态；
项目文档与当前代码使用同一层号、单位和节点语义。
```

ApiScan 算法、MapChannel 通道校验、WebSocket 网络安全和 OTA 来源认证不作为本轮完成
条件。
