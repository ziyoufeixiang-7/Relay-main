## 1. 文档目标与核心设计

项目的核心目标是让“实验算法”和“底层控制”解耦：

- 实验 API 决定输出什么物理量、如何形成节点、节点怎样跳转；
- `EngineCtrl` 把统一的 `ApiNodeData` 编译为硬件执行数据；
- `USEEngine` 只按 `USENode` 执行，不理解具体保护实验；
- `HWGateway` 只负责 UART 字节收发；
- 前端只与 JSON 协议交互，不直接操作 FPGA。

因此，一个实验通常只需在 API 中计算物理量，构造节点后调用
`EngineCtrl.upsertNodes()` 和 `EngineCtrl.trigNode()`，不需要自行处理串口帧、
ACK、跨线程投递或 FPGA 缓冲切换。

实际执行链为：

```text
前端 JSON
  -> WSGateway（主 asyncio 事件循环）
  -> EngineCtrl
  -> BaseApi 子类（例如 ApiScanTest）
  -> ApiNodeData
  -> EngineCtrl 编译
  -> EngineBridge（跨线程投递）
  -> USEEngine（硬件线程 asyncio 事件循环）
  -> HWGateway
  -> UART
  -> FPGA
```

反向事件链为：

```text
FPGA ACK / DI
  -> HWGateway
  -> USEEngine
  -> EngineBridge
  -> EngineCtrl.onEvent()
  -> activeApi.onUpdate()/onDi()
  -> WSGateway
  -> 前端 JSON
```

## 2. 代码依据与说明边界

仓库只有 FPGA bitstream 和下载工具，没有 HDL、寄存器实现或可审阅的 FPGA 工程；仓库也没有实际生产前端源码或部署后的 `index.html`。因此：

- Base/Shadow/Active、谐波频率派生、溢出策略和相位门控内部行为，是“Python 代码 + 当前协议文档所表达的设计”，不能由本仓库独立证明与当前 bitstream 完全一致；
- 本文能准确说明后端接收和返回的 JSON，但不能证明实际前端如何校验、组包或展示这些字段；
- FPGA 内部饱和、门控抢占和 DI 特殊状态编码需要结合当前 bitstream 真机确认；
- 本文中的“当前行为”均以 Python 实际调用链为准，不把旧文档中的目标设计当作已经实现。

## 3. 当前架构与“实验/控制解耦”

### 3.1 三层职责

| 层 | 主要对象 | 应负责的内容 | 不应负责的内容 |
|---|---|---|---|
| 实验层 | `BaseApi` 子类 | 解析实验参数、计算物理量、构建节点图、处理 DI/报告 | 串口、ACK、跨线程调度 |
| 控制/编译层 | `EngineCtrl` | 生命周期、API 路由、物理量转寄存器、节点编译、遥测、前端回复 | 具体保护实验数学 |
| 执行层 | `USEEngine` | 按 `USENode` 执行帧、定时、DI/超时/计数跳转、DO 时序 | 理解前端 JSON 或实验业务 |

正常实验 API 都经过上述三层。`AutoCal` 是特殊控制路径：它通过
`EngineBridge.sendBytes()` 直接发送校准帧，不构造普通实验节点；其运行流程在后文
单独说明。

### 3.2 `logic/` 全文件职责

| 文件 | 当前实际职责 |
|---|---|
| `FPGACodec.py` | 通道映射、物理标称比例、SYS/PARAM 帧编码、反馈解码及软件可见 FPGA 指令常量 |
| `Calibration.py` | 加载 `config/calibration.json`；在物理量与校准后寄存器量之间双向转换 |
| `USEEngine.py` | 硬件侧常驻节点状态机；帧/ACK、DI/DO、定时、超时、手动触发及四种 mode 的实现代码 |
| `EngineBridge.py` | 用 `call_soon_threadsafe()` 在主事件循环与硬件事件循环之间投递命令和事件 |
| `EngineCtrl.py` | API 生命周期、节点编译、功放启停、软件状态/遥测、前端消息分发和统一实验接口 |
| `HWProtect.py` | GPIO 功放/蜂鸣/硬件故障输入，以及基于主控寄存器状态估算的虚拟热模型 |
| `AutoCal.py` | DMM 驱动、AC/DC 标定与验证、直接 FPGA 控制和标定文件保存 |
| `SysConfig.py` | OTA/回滚子进程、USB 扫描挂载、Wi-Fi 扫描/连接/遗忘等系统管理 |

与它们直接相连的入口是：`SysEngine.py` 负责装配两个事件循环和各对象；
`BaseApi.py`/`Registry.py` 负责实验 API 创建；`Updater.py` 是 SysConfig 启动的独立
更新脚本；`ApiScanTest.py` 是本文用于解释实验层如何构造节点的主要实例。

### 3.3 当前不是“多进程架构”

`SysEngine.py:32-57` 创建硬件线程和独立事件循环，`SysEngine.py:65-87` 在主线程运行 WebSocket 与控制器。两者通过同一进程内的 `EngineBridge` 交互。

因此，`docs/architecture_overview.md` 中关于 `EngineProxy`、`HwEngineProcess`、TCP 8081、pickle IPC 和独立子进程的描述已经过时；当前仓库也不存在这些源码文件。

若 CPU affinity 成功：

- 主线程被固定到 CPU 2（`SysEngine.py:8-11`）；
- 硬件线程被固定到 CPU 3（`SysEngine.py:34-37`）。

## 4. FPGA 通讯帧、指令与运行原理

### 4.1 通道模型

前端/API 使用连续通道编号，`HWConfig.MapChannel()` 映射为 FPGA 物理通道：

| API 通道 | 物理通道 | 类型 |
|---:|---:|---|
| 0,1,2,3,4,5 | 0,2,4,6,8,10 | 电压 |
| 6,7,8,9,10,11 | 1,3,5,7,9,11 | 电流 |
| 12,13,14,15 | 12,13,14,15 | 保留 |

证据：`logic/FPGACodec.py:17-31`。

当前产品实验使用 API 通道 `0..11`；`12..15` 是底层编号表中的保留通道。

### 4.2 两种发送帧

#### 系统帧

长度 4 字节：

```text
0x5A | cmd_u8 | param_u8 | xor
```

校验字节为前三个字节 XOR。构造见 `logic/FPGACodec.py:73-81`。

#### 参数帧

长度 14 字节：

```text
0xA5 | cmd | regIndex | chMask_hi | chMask_lo
     | p1_u32_be | p2_u32_be | xor
```

构造见 `logic/FPGACodec.py:83-99`。`EngineCtrl._compileDictToFrames()` 会把具有相同 `(layer, p1, p2)` 的多个物理通道合并为一个 `chMask`，见 `logic/EngineCtrl.py:179-187`。

### 4.3 当前代码可发出的系统指令

| 代码 | 常量 | 代码表达的含义 | 当前调用情况 |
|---:|---|---|---|
| `0x00` | `SYS_START` | 启动波形发生 | Node 0、AutoCal |
| `0x01` | `SYS_STOP` | 停止波形发生 | 已定义，但生产控制链未使用 |
| `0x04` | `SYS_RESET` | FPGA 全局硬复位/清缓冲 | Node 0、Node FFFF、AutoCal |
| `0x05` | `SYS_UPDATE` | Active/Shadow 乒乓翻转 | 所有波形模式 |
| `0x06` | `SYS_SYNC` | Active 反写 Base 和 Shadow，三区对齐 | 每次进节点、Sweep |
| `0x20` | `SYS_SET_DBNC` | 设置 DI 防抖寄存器 | Node 0 |
| `0x21` | `SYS_SET_DO` | 写 8 位 DO | DO 时序、Reset 模式 |

证据：`logic/FPGACodec.py:50-67`。

当前普通停止流程使用“主控先关闭 GPIO 功放，再让状态机进入 FFFF 并发送
`SYS_RESET`”；`SYS_STOP` 虽已定义，但普通实验控制链没有调用它。

### 4.4 当前代码可发出的 DDS 参数指令

| 代码 | 常量 | Base | Shadow | Active | 当前调用 |
|---:|---|---|---|---|---|
| `0x10` | `DDS_WR_SHADOW` | 覆盖 | 同步新值 | 不变 | `base`、AutoCal |
| `0x11` | `DDS_WR_STAGE` | 不变 | 覆盖 | 不变 | `reset` |
| `0x14` | `DDS_STEP_SHADOW` | `Base += delta` | 同步累加结果 | 不变 | `steps` |
| `0x15` | `DDS_STEP_STAGE` | 不变 | `Shadow += delta` | 不变 | 已定义，当前未使用 |
| `0x1F` | `DDS_PHASE_GATE` | 特殊 | 特殊 | 到相位时翻转 | 可编译，但 Mode 4 已禁用 |

当前 `docs/fpga_protocol.md` 还记录了 `0x12/0x13/0x16/0x17` 四个“写/步进后自动翻转”指令，但 Python 代码没有常量或调用点。没有 HDL 时，应把它们视为协议文档中的候选指令，而不是已经由当前 bitstream 验证的能力。

### 4.5 Base / Shadow / Active 三级缓冲

当前协议表达的模型是：

| 缓冲 | 精度/作用 | 如何改变 |
|---|---|---|
| Base | 32 位累加锚点，保留步进小数精度 | WR、STEP、SYNC |
| Shadow | 下一次输出的预装载区，物理输出取高 16 位 | WR/STEP 自动同步，或 STAGE 单独写 |
| Active | 当前 DAC 输出 | `SYS_UPDATE` 与 Shadow 翻转 |

`SYS_SYNC` 把当前 Active 反写 Base 和 Shadow。它有两个作用：

1. 节点切换时把没有被新节点显式覆盖的通道/层保持在当前物理值；
2. 清掉 Shadow 中上一次 ping-pong 留下的旧值，避免下一次 UPDATE 把旧值翻回来。

### 4.6 相位门控

`BuildPhaseGateFrame()` 不把参数帧的 `chMask` 当位掩码，而写入 `physical_ch << 6`，见 `logic/FPGACodec.py:101-103`。

协议文档解释 FPGA 内部按 `16 通道 × 64 交流层 = 1024` 个计算位置循环，相位门控需要匹配某通道第一个计算位置，所以使用 `物理通道号 × 64`。门控帧在目标相位前不返回 ACK，并阻塞 FIFO，后续 SYNC/STEP 可提前排队。

这部分缺少 HDL 直接证据，而且 Mode 4 当前不可执行。

### 4.7 FPGA 反馈帧与 ACK

`HWGateway` 先寻找同步字节 `0x55`，再读取 6 字节，按小端 `<IH` 解析为：

```text
timestamp_u32 | status_u16
```

证据：`logic/FPGACodec.py:106-109`、`comms/HWGateway.py:28-45`。

`USEEngine.HandleHwFeedback()` 的解释为：

- `status == 0x0000`：成功 ACK；
- `status == 0xFFFF`：硬件通信错误；
- 其他值：DI 事件，DI 为低 8 位。

反馈帧没有在 Python 侧校验长度之外的 CRC/XOR。还必须向 FPGA 团队确认：DI=0 和 DI=255 如何与两个保留状态值区分。现有模拟测试为了表示“DI 变为 0 但不是 ACK”，会发送 `0x0100`，暗示硬件反馈可能有未在本文档中正式定义的类型标志。

## 5. 0 到 64 层的准确含义

这是整个数据结构中最容易误解的部分。

### 5.1 API 层号不是 FPGA `regIndex` 原值

`EngineCtrl` 的映射公式是：

```python
regIndex = (api_layer - 1) & 0xFF
```

证据：`logic/EngineCtrl.py:185`。

因此：

| API 层号 | FPGA Index | `[p1, p2]` 物理含义 | 作用 |
|---:|---:|---|---|
| 0 | `0xFF` | `[直流偏置幅值, 公共基准频率 Hz]` | DC 分量 + 本通道交流层基频 |
| 1 | `0x00` | `[基波幅值, 基波相位 °]` | 1 次交流分量 |
| 2 | `0x01` | `[2 次谐波幅值, 相位 °]` | 2 次谐波 |
| ... | ... | ... | ... |
| 64 | `0x3F` | `[64 次谐波幅值, 相位 °]` | 第 64 个交流层 |

`Calibration.PhysToReg()` 也只在 `layerIdx == 0` 时把第二个值当频率；所有非 0 层都把第二个值当相位，见 `logic/Calibration.py:36-52`。

所以：

- “layer 0 是基波幅值”是错误说法；
- layer 0 的幅值是 DC/零偏分量，频率是所有交流层的公共基频；
- 真正的基波幅值和相位在 layer 1；
- layer N（1..64）对应 N 次交流/谐波分量。

`docs/experiment-implementation-logic/05-status-sequence.md:86-93` 把 layer 0 描述成基波正弦幅值，与当前代码和 FPGA 参数协议冲突，不应继续作为接口依据。

### 5.2 有效层范围

有效 API 层号是 `0..64`。编译公式使用 U8 掩码，因此其他层号会出现下列别名：

- layer 65 -> FPGA `0x40`，超出文档定义的交流层范围；
- layer 256 -> FPGA `0xFF`，误写 DC/频率层；
- layer 257 -> FPGA `0x00`，误写基波；
- 负层号也会别名到其他 Index。

API 实验代码只能构造 `0..64` 层；其他数值不属于当前 FPGA 层协议。

### 5.3 频率与谐波

代码和当前协议设计表示：layer 0 提供公共基频，FPGA 对 layer 1..64 按层次派生 `N × 基频`。例如 `ApiDiffTest.py:521-531` 用 layer 1 写基波、用 layer N 写 N 次谐波。

由于缺少 HDL，应在硬件联调中再次确认 layer 64、负/过高频率、频率步进饱和和相位关系。

## 6. 物理量到寄存器的转换

### 6.1 标称比例

`HWConfig` 当前定义：

| 量 | 公式/比例 |
|---|---|
| 电压幅值 | `0x7FFF0000 / 200` |
| 电流幅值 | `0x7FFF0000 / 60` |
| 相位高 16 位 | `65536 / 360` |
| 频率 U32 | `2^32 / 40_000_000 × 1024` |
| 防抖寄存器 | `50000 / 16384` 每毫秒 |

对应数值：

- 电压：`10,737,090.56 reg/V`
- 电流：`35,790,301.866... reg/A`
- 相位：`182.0444... code/°`，随后左移 16 位
- 频率：`109,951.1627776 reg/Hz`
- 防抖：每寄存器单位 `0.32768 ms`
- 可无绕回表达的防抖上限约 `83.5584 ms`

证据：`logic/FPGACodec.py:4-15,34-48`。

### 6.2 校准

配置格式为：

```json
{
  "物理通道": [bias, factorDc, factorAc]
}
```

绝对值转换：

- layer 0 幅值：`physical × factorDc + bias`
- layer 1..64 幅值：`physical × factorAc`
- layer 1..64 相位：物理相位额外加 180° 后编码

步进增量转换 `is_delta=True`：

- 不加 DC bias；
- 不加 AC 绝对相位的 180°。

因此，`steps` 必须使用 `physDictToReg(..., is_delta=True)`。如果把绝对转换用于 step，每一步都会重复加入 bias 或 180°。

### 6.3 编码边界行为

`ConvertAmpToReg()`、`ConvertFreqToReg()` 和 `ConvertDbncToReg()` 按比例计算后使用位掩码
得到目标寄存器宽度，见 `logic/FPGACodec.py:34-48`。

例如，100 ms 防抖先计算为 305，再 `& 0xFF` 变成 49，最终硬件值约为
16.06 ms。这是理解当前寄存器编码时需要考虑的 U8 回绕行为。

因此，寄存器编码层表达的是确定的位级转换，不负责替代实验参数的物理范围定义。

## 7. `USENode` 与 `ApiNodeData`

### 7.1 两种数据的边界

`ApiNodeData` 定义在 `api/BaseApi.py:13-32`，是 API 到控制器的统一中间结构。

对于正常实验 API，`ApiNodeData.base/reset/steps` 已经不是前端浮点字典，而是：

```text
Dict[
  物理通道 int,
  Dict[
    API 层号 int,
    [ampReg_u32, freqOrPhaseReg_u32]
  ]
]
```

转换发生在 `BaseApi.physDictToReg()`，见 `api/BaseApi.py:74-81`：

1. JSON 通道键和层键由字符串转 `int`；
2. API 通道经 `MapChannel()` 变成 FPGA 物理通道；
3. 物理浮点经 Calibration 变成寄存器。

`USENode` 定义在 `logic/USEEngine.py:8-27`。它不再保存寄存器字典，而保存已经编译好的 `bytes` 帧。

### 7.2 全字段含义

| `ApiNodeData` | 编译后的 `USENode` | 含义与约束 |
|---|---|---|
| `mode` | `mode` | 1=Static，2=Sweep，3=Reset；4 当前禁用 |
| `interval` | `interval` | Mode 2/3 使用，单位毫秒，必须为正有限数 |
| `resetTime` | `resetTime` | Mode 3 复归段时长，单位毫秒 |
| `base` | `baseFrame` | 绝对值，编成 `DDS_WR_SHADOW` |
| `reset` | `resetFrame` | 复归绝对值，编成 `DDS_WR_STAGE` |
| `steps` | `stepFrames` | 每 tick 一个增量字典，编成 `DDS_STEP_SHADOW` |
| `gate` | `gateFrames` | `[物理通道, phase_u32]`；当前 Mode 4 不执行 |
| `resetDo` | `resetDo` | 低 8 位=复归段 DO，高 8 位=动作段 DO |
| `doActions` | `doActions` | 每项 `(delay_ms << 8) | do_u8`，相对节点基准生效时刻 |
| `countOverId` | 同名 | step 全部完成后的节点目标；None=保持末值 |
| `diMatchMask` | 同名 | 低8位DI，另有 AND/参考/反相标志 |
| `diMatchId` | 同名 | DI 命中的节点目标 |
| `timeoutMs` | 同名 | 节点超时，单位毫秒 |
| `timeoutId` | 同名 | 超时节点目标 |

dataclass 类型标注不会做运行时校验。除 `mode` 外所有字段都默认 `None`。

### 7.3 DI 匹配的精确判式

`diMatchMask` 的位含义：

| 位 | 含义 |
|---:|---|
| `0x001..0x080` | 8 路 DI 选择 |
| `0x100` | 1=所有选中位都满足；0=任一选中位满足 |
| `0x200` | 参考进入当前节点时的 `diPrev`；否则参考离开 Node 0 时的 `diStart` |
| `0x400` | 把参考电平取反 |

代码判式见 `logic/USEEngine.py:170-178,321-328`：

```text
ref = (diPrev 或 diStart) XOR (invert ? 0xFF : 0)
changed = (diNow XOR ref) AND low8Mask
OR  模式：changed != 0
AND 模式：changed == low8Mask
```

`0x500 = AND + 反相` 常用于“所有触点都恢复到试验起始状态”。

### 7.4 DO 打包

`doActions` 每项：

```text
bits 8..23 : 延迟毫秒（执行时只取 16 位）
bits 0..7  : DO 值
```

动作按列表顺序执行；调用方应按延迟排序。

`resetDo`：

```text
bits 0..7  : enterDo，复归输出期间
bits 8..15 : exitDo，动作/故障输出期间
```

Mode 3 当前不调用普通 `doActions`，只使用 `resetDo`，见 `logic/USEEngine.py:237-257`。

### 7.5 节点 ID 红线

可写的实验节点 key 必须为：

```text
1 <= nodeId <= 0xFFFE
```

保留节点：

- `0x0000`：初始化/零输出/预热；
- `0xFFFF`：终止/复位/DO 清零。

“禁止写入保留 ID”不等于“禁止跳转到 `0xFFFF`”。实验出口可以把 `0xFFFF` 作为终止目标，但不得把自定义 `ApiNodeData` 写入该 key。

普通实验内部也不应把 `0x0000` 当点间节点：`USEEngine.py:337-340` 在跳到 0 或 FFFF 时会清除所有临时节点，只保留两个保留节点。

API 评审时必须检查每一次 `upsertNodes()`：字典 key 中不得出现 `0` 或
`0xFFFF`。允许把它们用作系统触发目标或节点跳转目标，但不能重新定义对应节点。

### 7.6 一个正确的构造示例

下面只演示结构，不代表产品允许的最终幅值范围：

```python
base_phys = {
    "6": {                    # API ch6 -> 第一组 A 相电流
        "0": [0.0, 50.0],    # DC=0，公共基频=50Hz
        "1": [1.0, 0.0],     # 基波幅值1，相位0°
        "2": [0.1, 30.0],    # 二次谐波幅值0.1，相位30°
    }
}

step_phys = {
    "6": {
        "1": [0.05, 0.0],    # 每步基波幅值增加0.05
    }
}

node = ApiNodeData(
    mode=2,
    interval=100,            # 100ms
    base=self.physDictToReg(base_phys),
    steps=[
        self.physDictToReg(step_phys, is_delta=True)
        for _ in range(10)
    ],
    countOverId=0xFFFF,
    diMatchMask=0x01 | 0x200,
    diMatchId=0xFFFF,
)

assert self.ctrl.upsertNodes({1: node})
self.ctrl.trigNode(1)
```

构造器之外仍应有统一验证器，至少保证：

- 节点 ID 不写 0/FFFF；
- 通道为 API 0..11，转换后为物理活动通道；
- 层为 0..64；
- 每个值恰好两个有限数；
- Mode 2/3 的时间和 steps 组合完整；
- 所有 stepped channel/layer 都在初始 state 中有基准；
- 每个累计 step 都在设备安全范围；
- 所有跳转目标存在，或是明确允许的 FFFF 终止；
- `doActions` 有序且 DO 只用低 8 位。

## 8. `USEEngine` 的状态机与波形模式

### 8.1 永久状态机

`USEEngine.start()` 创建 `coreLoop()`，之后引擎一直在节点之间跳转。没有独立的“Stopped 对象状态”；所谓待机和终止是停留在保留节点。

#### Node 0

定义见 `logic/USEEngine.py:38-43`：

```text
SYS_RESET
-> 12 个活动物理通道的 layer0 写入 [校准后零幅值, 50Hz]
-> SYS_START
-> SYS_SET_DBNC
-> runStatic 追加 SYS_UPDATE
-> 等待下一次触发
```

#### Node FFFF

定义见 `logic/USEEngine.py:44`：

```text
SYS_RESET
-> runStatic 追加 SYS_UPDATE
-> DO=0
```

当 `EngineCtrl` 收到 nodeId=FFFF 的 value update，会关功放、调用 API `onStop()`、发 error/report/stop、清理主控状态并置 `_stopEvent`，见 `logic/EngineCtrl.py:37-45,97-111`。

### 8.2 每次进节点的公共步骤

`coreLoop()` 在每个节点前：

1. 找不到目标节点时静默改进 FFFF；
2. 尝试取消遗留 DO 任务；
3. 清触发事件；
4. 下发 `SYS_SYNC`；
5. 保存 `diPrev`；
6. 安装 timeout 和 DI 判据；
7. 按 mode 执行。

见 `logic/USEEngine.py:298-341`。

### 8.3 Mode 1：Static

见 `logic/USEEngine.py:200-205`：

```text
baseFrame + UPDATE
-> emit tick=0
-> 启动 doActions
-> 启动 timeout
-> 等待 manual / timeout / DI
```

如果没有出口，代码会调用 `sleepForever()`。这个名字并不准确：它把绝对唤醒点
设为当前节点基准时刻加 100000 秒；若配置了更早的 timeout，则 timeout 优先。
没有任何触发时最终仍会返回 FFFF，上限约为 27 小时 46 分 40 秒，并不是真正的
永久保持。

### 8.4 Mode 2：Sweep

见 `logic/USEEngine.py:207-228`：

```text
base + UPDATE                         # 基准生效，tick0
SYNC + step[0]                       # 三区对齐并预载第一步
等待 interval
UPDATE                               # step0 生效，tick1
预载 step[1]
等待 interval
...
最后一步生效后再保持一个 interval
-> countOverId，或进入约 100000 秒的长等待
```

若 `count = len(steps)`，从基准生效到 countOver 跳转共经历 `count + 1` 个 interval：基准一个驻留区间，每个 step 各一个驻留区间。

`steps` 为 `None` 或空列表时，Mode 2 静默退化为 Static，`countOverId` 不会执行；
同样会受上述 `sleepForever()` 上限影响。

### 8.5 Mode 3：Reset

见 `logic/USEEngine.py:230-261`。设：

- `F`：base 故障/动作基准；
- `R`：reset 复归值；
- `sN`：第 N 个增量。

实际流程：

```text
WR_SHADOW(F) + WR_STAGE(R) + UPDATE  # R 生效，emit tick=-1
DO=enterDo
WR_SHADOW(F)                         # F 预载回 Shadow
等待 resetTime（只响应 manual）

UPDATE                               # F 生效，emit tick=0
DO=exitDo
等待 interval（评估 manual/timeout/DI）

UPDATE                               # R 再生效，emit tick=-1
DO=enterDo
STEP_SHADOW(s0)                      # 复归窗口中，Base 累加并把 F+s0 预载
等待 resetTime（只响应 manual）

UPDATE                               # F+s0 生效，emit tick=1
DO=exitDo
等待 interval
...
```

关键点：

- `base` 必须保存动作态累加锚点；
- `reset` 只写 Shadow，不能污染 Base；
- Mode 3 必须同时有非空 steps 和非 `None` 的 `resetDo`，否则静默退化为 Static；
- 当前 timeout 从初始 R 生效时开始计时，但 reset 窗口不评估；如果 timeout 在 reset 期间已经到点，会在进入下一个普通等待后立即触发；
- 正常 `doActions` 在 Mode 3 被注释，不执行；
- 总时长包含初始 R/F 和每个 step 的 R/F，即约为 `(count + 1) × (resetTime + interval)`，除非被其他触发提前打断。

### 8.6 Mode 4：DcComp

`runDcComp()` 的实现仍在 `logic/USEEngine.py:263-296`，`EngineCtrl` 也能生成 gate 帧，但 `coreLoop()` 的 `case 4` 已在 `logic/USEEngine.py:329-334` 注释。

所以当前事实是：

- `mode=4` 不输出文档所称的直流补偿波形；
- 它会走默认分支，把 nextId 设为 FFFF；
- `ApiScanTest` 也没有读取 `dcComp` 或 `prevStatics`。

现有文档中把 DcComp 描述为可用功能的内容属于目标设计，不是当前运行能力。

### 8.7 触发优先级和等待精度

`_evalTrig()` 优先级：

1. manual trigger；
2. timeout；
3. DI。

普通 `sleep()` 每最多约 25 ms 轮询一次，同时可被 DI event 唤醒；最后约 2 ms 使用忙等提高时序精度。`sleepWait()` 只检查 manual，不检查 DI 和 timeout。

- `manualTrig()` 只是覆盖单个 `trigTarget`，没有队列、锁或“FFFF 最高优先级”；
- manual trigger 不会直接 set event，最坏要等轮询或 ACK 流程返回；
- 最后 2 ms 忙等期间，硬件线程 event loop 暂不调度串口 reader 和其他协程。

### 8.8 ACK 计数

`flush()`：

1. 获取 `hwLock`；
2. 记录目标 `sentCount + frameCount`；
3. 逐帧发送并增加 `sentCount`；
4. 等 `ackCounter >= target`。

任意连续 100 ms 没有新 ACK，会记 `ACK timeout` 并触发 FFFF。硬件返回 FFFF 会记 `HW communication error`。

这个计数模型基于以下协议关系：

- FPGA 对每个物理帧恰好回复一个 ACK；
- 每条进入该调度器的发送路径需要同步维护 `sentCount`；
- 不允许把 DI 错认成 ACK。

## 9. `EngineCtrl` 接口与生命周期

### 9.1 实验 API 使用的核心接口

| 接口 | 作用 |
|---|---|
| `upsertNodes({id: ApiNodeData})` | 编译并上传/覆盖节点 |
| `trigNode(id)` | 请求状态机跳转 |
| `stopTest(reason=None)` | 立即关功放并请求进入 FFFF |
| `sendReport(data)` | 向前端发实验报告 |
| `sendValueUpdate(...)` | 向前端发物理量更新 |
| `sendError(msg)` | 向前端发错误 |
| `sendDi()/sendDo()` | 向前端发数字量状态 |

实验 API 不应调用 `engine.sendBytes()` 或 `HWGateway`。

### 9.2 当前 start 流程

`logic/EngineCtrl.py:59-86`：

1. 若 AutoCal 正在运行，拒绝；
2. 获取 `_startLock`；
3. 若前一实验未完整终止，写 `manualTrig(FFFF)` 并无限等待 `_stopEvent`；
4. 清 `_stopEvent`；
5. 根据 `module` 创建 API；
6. 清主控 DO/state/nodes；
7. 设置防抖；
8. `manualTrig(0)`；
9. `running=True`；
10. 立即启功放；
11. 固定等待 100 ms；
12. 调用 `activeApi.setup(params)`。

当前 100 ms 是固定等待时间，不是显式的 Node 0 完成握手；这是理解现有启动时序时
需要区分的两个概念。

### 9.3 编译

`EngineCtrl._compileNode()` 将：

- `base` -> `DDS_WR_SHADOW`
- `reset` -> `DDS_WR_STAGE`
- 每个 step -> `DDS_STEP_SHADOW`
- gate -> `DDS_PHASE_GATE`

然后构造 `USENode`，见 `logic/EngineCtrl.py:179-211`。

### 9.4 遥测

`EngineCtrl._handleValueUpdate()`：

- tick 0：把 base 写入主控 `state`，立即上报；
- tick -1：上报 reset，但不更新 `state`；
- tick >0：在 `state` 中累加 step；最后一步或距离上次上报 50 ms 时发送。

见 `logic/EngineCtrl.py:213-233`。

这意味着：

- 主控 state 是软件推导值，不是 FPGA 回读值；
- 寄存器量化可逆转换后才发前端；
- reset 输出不会进入 state，因此 HWProtect 当前继续使用上一份主控 state。

### 10.3 节点图

#### 手动模式

```text
Node 0 预热
  -> Node 1 Static
       DI -> FFFF

update_static:
  Node 1 <-> Node 2 ping-pong
```

见 `api/ApiScanTest.py:107-120,365-397`。

#### 单向自动扫描

```text
[可选 Node1 预试复归，timeout -> 2]
Node2 正向 Mode2/Mode3
  DI -> FFFF
  countOver -> FFFF
```

#### 动作-返回扫描

`changeMode=1, returnMode=0`：

```text
Node2 正扫
  DI -> Node3 反扫
  countOver 未动作 -> FFFF

Node3
  所有选中 DI 恢复 -> FFFF
  countOver -> FFFF
```

Node3 使用 `logicMask | 0x500`，即 AND + 反相。

#### 全正反扫

`changeMode=1, returnMode!=0`：

```text
Node2 跑满 count -> Node3
Node3 跑满 count -> FFFF
```

Node3 的 `base={}` 是有意设计：进节点前的 `SYS_SYNC` 已把 Node2 当前 Active 同步到 Base/Shadow，空 base 使反扫从当前值继承。

Node3 无论 Node2 实际走到第几步，都固定生成 `count` 个负 step。若正扫在第
`k<count` 步进入 Node3，并一直执行到 countOver，则末值按当前代码为：

```text
statics + (k - count) × step
```

通常动作-返回流程会在 DI 恢复时提前进入 FFFF；上式描述的是没有提前恢复而完整执行
Node3 时的实际数值路径。

1. EngineCtrl 在 Node0 后固定等待 100 ms；

## 12. AutoCal 自动校准执行原理

### 12.1 控制入口

`EngineCtrl` 在初始化时创建 `AutoCal`，传入三个能力：

```text
前端发送函数
EngineBridge.sendBytes() 原始 FPGA 发送函数
EngineCtrl.setAmplifier() 功放控制函数
```

前端发送 `cmd=autoCal` 后，`EngineCtrl.HandleCommand()` 把整条消息交给
`AutoCal.handle_command()`。支持的 action 为：

| action | 作用 |
|---|---|
| `auth` | 建立当前进程内的校准授权状态 |
| `start` | 对一个通道执行 AC/DC 系数标定 |
| `verify` | 加载当前系数并逐点验证 |
| `stop` | 设置停止标志，由校准循环在检查点退出 |

AutoCal 不构造 `ApiNodeData`，而是直接发送 FPGA 帧：

```text
AutoCal
  -> EngineBridge.sendBytes()
  -> USEEngine._send()
  -> HWGateway.WriteBytes()
  -> UART / FPGA
```

### 12.2 FPGA 校准输出

每个校准步骤先执行：

```text
SYS_RESET
等待 10 ms
SYS_START
等待 10 ms
```

直流输出使用逻辑层 0 对应的 `regIndex=0xFF`：

```text
DDS_WR_SHADOW(0xFF, channelMask, amplitudeReg16 << 16, 0)
SYS_UPDATE
```

交流输出使用基波层对应的 `regIndex=0x00`：

```text
DDS_WR_SHADOW(0x00, channelMask, amplitudeReg16 << 16, 0)
SYS_UPDATE
```

这里传入的是直接寄存器值，不经过普通实验的 `Calibration.PhysToReg()`。

### 12.3 DMM 与四点标定

AutoCal 通过 PyVISA 选择可用 DMM 资源，设置 5 秒查询超时。对每个步骤：

1. 配置 DMM 测量档位；
2. 复位并启动 FPGA；
3. 下发指定 AC 或 DC 值；
4. 等待约 5 秒稳定；
5. 周期读取 `:READ?`；
6. 计算样本均值和总体方差。

电流通道每个点采样约 30 秒，电压通道每个点约 10 秒。标定点为：

| 通道类型 | AC 点 | DC 零点 | DC 正点 | DC 负点 |
|---|---:|---:|---:|---:|
| 电流 | 0.5 A | 0 A | +0.5 A | -0.5 A |
| 电压 | 57.735 V | 0 V | +100 V | -100 V |

AC 寄存器按峰值写入，因此代码对目标有效值乘 `sqrt(2)`。直流三点通过带样本方差
权重的直线拟合得到：

```text
measured = G_dc × commanded + O_dc
```

随后保存：

```text
bias     = -O_dc / G_dc
factorDc = 1 / G_dc
factorAc = 1 / G_ac
```

配置文件中每个物理通道的结构为：

```json
{
  "physical_channel": [bias, factorDc, factorAc]
}
```

### 12.4 验证流程

`verify` 会先调用 `calib.LoadCalib()`，再用校准后的 `PhysToReg()` 输出多个 AC/DC 点。
电流通道覆盖正负 DC 和多个 AC 档位；电压通道覆盖 ±10、±60、±110 V DC 以及
10、60、110 V AC。

每个验证点回传：

```json
{
  "module": "autoCal",
  "type": "verifyPoint",
  "target": 60.0,
  "measured": 59.98,
  "error": 0.03
}
```

进度使用 `calStatus`，错误使用 `calError`。完成或退出后执行 FPGA reset、关闭功放并
清理 `_running` 和 `_stop_flag`。

## 13. HWProtect 功放和热保护

### 13.1 GPIO 功能

当前定义：

| GPIO | 作用 |
|---:|---|
| 21 | 功放使能 |
| 26 | 蜂鸣器 |
| 20 | 硬件故障/过热输入 |

`EngineCtrl.setAmplifier()` 调用 `HWProtect.SetAmplifierEnable()` 改变功放 GPIO，并触发
一次提示音。硬件故障输入激活时，`HWProtect._TriggerProtection()` 先关闭功放，再调用
`EngineCtrl.stopTest(reason)`。

### 13.2 虚拟热模型

监控任务每约 200 ms 读取一次 `EngineCtrl.state`。对六个电流物理通道分别累计：

```text
DC layer power = signed_amp16²
AC layer power = signed_amp16² × 0.5
```

交流乘 0.5 是从峰值平方换算到正弦 RMS 平方。温度状态按：

```text
T_new = T_old × (1 - COEF_COOLING × dt)
        + total_power × COEF_HEATING × dt
```

更新。最大虚拟温度达到 100 时触发软件过热保护。功放关闭期间只执行冷却。

前端周期收到：

```json
{
  "type": "load",
  "thermal": 12.35,
  "active": true
}
```

这里的温度是相对热负载模型值，不是摄氏温度，也不是硬件传感器直接读数。

## 14. SysConfig 与 Updater

### 14.1 SysConfig 消息分派

`cmd=sysConfig` 的消息由 `SysConfig.handle_command()` 按 action 动态分派到对应异步
处理函数。主要 action 包括：

| action | 作用 |
|---|---|
| `checkUpdate` | 读取本地版本并查询远端 `version.json` |
| `startUpdate` | 从 web 或 USB 启动更新脚本 |
| `rollback` | 从 `.bak` 回滚 |
| `usbScan` | 扫描、尝试挂载 USB 并读取更新版本 |
| `wifiScan` | 扫描附近 Wi-Fi |
| `wifiConnect` | 按 SSID/密码连接 |
| `wifiSavedList` | 列出 NetworkManager 保存的连接 |
| `wifiConnectSaved` | 按 UUID 连接已保存网络 |
| `wifiForget` | 按 UUID 删除保存网络 |
| `wifiStatus` | 返回当前 SSID、信号和 IPv4 地址 |

普通外部命令通过 `asyncio.create_subprocess_exec()` 执行；更新任务单独启动
`/usr/bin/python3 Updater.py`，并把其 stdout 中逐行输出的 JSON 转发给前端。

### 14.2 更新文件

一次更新需要：

```text
backend.tar.gz
backend.tar.gz.sha256
index.html
index.html.sha256
version.json
```

web 更新从产品目录下载；USB 更新从挂载盘下的 `<PRODUCT>/` 读取。后端包和前端
页面分别做 SHA-256 一致性检查。

### 14.3 安装流程

`Updater._performUpdate()` 的当前顺序为：

```text
下载/复制到系统临时目录
  -> 校验 SHA-256
  -> 清空 installDir.new
  -> 解压 backend.tar.gz
  -> 放入 index.html 和 version.json
  -> 从现役目录继承 config/calibration.json
  -> os.sync()
  -> 现役目录改名为 .bak
  -> .new 改名为现役目录
  -> 设置 SysEngine.bin 可执行
  -> 回传 success
  -> systemctl restart --no-block relay-protection
```

回滚会把 `.bak` 复制到新的 staging 目录，继承当前设备的 calibration，再把现役目录
换成回滚目录并重启服务。

### 14.4 USB 与 Wi-Fi

USB 扫描使用 `lsblk` 查找 `/dev/sd*` 的未挂载分区，并尝试挂到 `/media/pi/<label>`。
随后在 `/media/pi/*/<PRODUCT>/` 中寻找更新目录。

Wi-Fi 管理由 `nmcli` 完成。扫描结果按 SSID 合并信号最强项，同时标记 active 和
saved；保存连接的连接/遗忘操作使用 UUID；连接状态额外查询无线接口 IPv4 地址。

## 15. 实验 API 编写规范

### 15.1 创建 API

一个 API 类继承 `BaseApi`，通过 `MODULE_KEY` 或 `MODULE_KEYS` 声明前端 module：

```python
class ApiExample(BaseApi):
    MODULE_KEY = "example_test"
```

`BaseApi.create()` 每次实验开始都会创建新实例。它首先动态扫描 `api/Api*.py`，
没有找到时再使用 `api/Registry.py` 中的类列表。

实验类通常实现：

```python
_onSetup(params)
onUpdate(nodeId, tick, hw_ts)
onDi(di, hw_ts)
onWebCommand(msg)
_onStop()
```

### 15.2 从物理量构造节点

前端物理量字典的通道和层键来自 JSON，因此是字符串：

```json
{
  "6": {
    "0": [0.0, 50.0],
    "1": [1.0, 0.0]
  }
}
```

API 使用：

```python
base_reg = self.physDictToReg(base_phys)
step_reg = self.physDictToReg(step_phys, is_delta=True)
```

完成字符串键转整数、API 通道到物理通道映射，以及校准后的物理量到寄存器转换。
不要把未经转换的前端 JSON 直接放进 `ApiNodeData.base/reset/steps`。

### 15.3 节点 ID 红线

> **任何 API 实验代码都禁止通过 `upsertNodes()` 写入或覆盖节点 `0x0000` 和
> `0xFFFF`。可写实验节点范围是 `0x0001..0xFFFE`。**

必须区分：

| 操作 | `0x0000` | `0xFFFF` |
|---|---|---|
| 作为 `upsertNodes()` 的 key | 禁止 | 禁止 |
| `trigNode(0)` | 系统初始化时允许 | — |
| `trigNode(0xFFFF)` | — | 停止时允许 |
| 作为 `timeoutId/diMatchId/countOverId` | 一般实验内部不使用 | 允许，表示终止 |

原因是：

- Node 0 内建了 FPGA reset、零幅值/50 Hz、DDS start 和 DI 防抖；
- Node FFFF 内建了 FPGA reset 和 DO=0；
- 进入任一保留节点会清除本轮普通节点；
- 覆盖保留节点会改变后续所有实验共同依赖的系统语义。

API 代码评审时，应逐项搜索：

```text
upsertNodes({0: ...})
upsertNodes({0x0000: ...})
upsertNodes({65535: ...})
upsertNodes({0xFFFF: ...})
```

这些写法一律不允许；把跳转目标设置为 `0xFFFF` 则是正常终止方式。

### 15.4 Mode 选择

| 需求 | mode | 关键字段 |
|---|---:|---|
| 固定输出并等待 DI/超时/手动命令 | 1 | `base`、触发字段 |
| 连续阶梯扫描 | 2 | `base`、`steps`、`interval` |
| 每步之间输出复归值 | 3 | Mode2 字段 + `reset/resetTime/resetDo` |
| 相位门控补偿 | 4 | 当前仅保留实现，不作为普通 API 可用模式 |

`base`/`reset` 是绝对值；`steps` 必须是增量值。Mode 3 的 `resetDo` 低 8 位是复归
DO，高 8 位是动作 DO。

### 15.5 注册和启动节点

推荐一次构造完整节点图：

```python
nodes = {
    1: node_prepare,
    2: node_test,
    3: node_return,
}

if not self.ctrl.upsertNodes(nodes):
    return
if not self.ctrl.trigNode(1):
    return
```

节点出口由 `diMatchId`、`timeoutId`、`countOverId` 或后续手动 `trigNode()` 表达。
需要终止时让节点跳转到 `0xFFFF`，不要自行定义终止节点。

### 15.6 回调和报告

- `onUpdate()` 只处理已实际生效的 node/tick；
- `tick=-1` 表示 Mode 3 复归态；
- `onDi()` 使用 FPGA U32 微秒时间戳；
- 物理状态由 API 原始数据和 tick 推导，不是 FPGA 模拟量回读；
- `_onStop()` 负责组装最终报告；
- `sendReport()`、`sendValueUpdate()`、`sendError()` 统一通过控制器发给前端。

完整抽象可以归纳为：

```text
前端物理参数
  -> API 数学和节点图
  -> physDictToReg
  -> ApiNodeData
  -> EngineCtrl 编译
  -> USENode / FPGA 帧
  -> USEEngine 节点事件
  -> API 计算结果
  -> 前端 report
```

## 16. 完整运行时序

### 16.1 系统启动

```text
进程启动
  -> 主线程设置 CPU affinity / uvloop
  -> 创建硬件 daemon 线程
  -> 硬件线程创建 HWGateway + USEEngine
  -> 主线程创建 EngineBridge
  -> 创建 WSGateway、HWProtect、EngineCtrl
  -> 相互绑定回调
  -> 等待 1 s
  -> 启动 USEEngine.coreLoop()
  -> 启动 WebSocket server
```

### 16.2 实验启动到首个实验节点

```text
start JSON
  -> EngineCtrl.startTest()
  -> 创建 API
  -> 设置 debounce
  -> manualTrig(Node 0)
  -> 开功放
  -> 等待 100 ms
  -> API.setup()
  -> API 构造节点
  -> 可选 API 预热
  -> upsertNodes()
  -> trigNode(firstId)
```

### 16.3 节点输出

```text
进入节点
  -> SYS_SYNC
  -> 安装 DI/timeout 条件
  -> 按 mode 写 Base/Shadow
  -> SYS_UPDATE
  -> FPGA ACK
  -> emit node/tick/timestamp
  -> EngineCtrl 更新 state
  -> API onUpdate()
  -> 前端 value_update
```

DI 变化时：

```text
FPGA DI + timestamp
  -> USEEngine 更新 diNow
  -> emit DI
  -> EngineCtrl / API / 前端
  -> 若节点 DI matcher 命中，跳转目标节点
```

### 16.4 停止

```text
stop 命令、DI/timeout/countOver -> FFFF，或保护触发
  -> 关闭功放
  -> manualTrig(FFFF)
  -> FFFF: SYS_SYNC + SYS_RESET + UPDATE + DO0
  -> EngineCtrl 收到 FFFF tick
  -> API.onStop()
  -> report/error/stop
  -> 清 activeApi、state、nodes
  -> running=False
  -> _stopEvent.set()
```

## 17. 需要结合 FPGA 或真机确认的协议点

以下内容不能只由 Python 代码证明：

1. SYS/PARAM 帧 XOR 校验失败时 FPGA 的反馈；
2. `status_u16` 如何区分 ACK、非法指令、DI=0 和 DI=255；
3. RESET 后 Active/Shadow/Base、DO、DI debounce 的准确复位值；
4. UPDATE 的精确交换方向以及连续两次 UPDATE 的结果；
5. layer 1..64 的谐波频率派生和 layer 64 是否全部可用；
6. 幅值、频率、相位和连续 step 的硬件饱和/溢出规则；
7. SYS_SYNC 是否确实对全部通道和层反写；
8. Phase Gate 等待期间 STOP/RESET 是否能抢占；
9. 功放使能 GPIO 在掉电、进程崩溃和系统重启时的默认电平；
10. 硬件故障输入是否能不依赖 Python 独立切断功放。
