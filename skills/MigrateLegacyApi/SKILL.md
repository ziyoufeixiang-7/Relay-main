# MigrateLegacyApi 技能指南

当你接到将 `oldrelay` 下的旧架构实验（例如反时限、滑差、状态序列等）移植到新架构 `BaseApi` 上的任务时，你**必须**严格遵守本指南。

## 1. 强制移植工作流与高频交互 (Mandatory Workflow & Grill-Me)

在开始写任何代码之前，必须严格执行以下步骤，并在整个过程中**高频使用 `/grill-me` 与用户消除模糊地带**：

1. **结合现有技能**：你必须全程结合使用 `skills/DevelopApiExperiment/SKILL.md`。移植不是简单的生搬硬套旧代码的逻辑，必须用开发新实验的标准来重新审视旧代码。
2. **通读旧版设计文档并梳理疑点**：查看 `oldrelay/docs/api/` 下对应实验的 Markdown 文档，彻底搞懂该实验在物理学和继电保护专业上的目的和实现路径。
3. **高频交互确认 (/grill-me)**：在动手写新代码前，你**必须**主动发起一系列问答来澄清所有的历史遗留模糊点：
   - **深挖历史意图**：对于旧代码中那些晦涩的“黑魔法”（例如奇怪的延时桩节点、硬编码的参数处理、非标准的前端变量），坚决不能盲目翻译，必须通过 `/grill-me` 询问用户的真实物理意图。
   - **重构方案碰撞**：主动向用户提出“如何将旧版的 `InterceptWsEvent` 状态机拦截映射到新版的 `ApiNodeData` 和 `onUpdate`/`onDi` 回调体系中”的草案，并在问答中达成共识。
   - **测试覆盖范围**：确认在接下来的 Python 拦截模拟测试中，具体需要抓取、打印和比对哪些关键物理字段。
4. **起草实施计划并请求审核**：将你的重构计划写在 `implementation_plan.md` 中。
5. **生成新版代码并编写一致性 Test 脚本**（详见后文第 3 节的绝杀测试方案）。

## 2. 架构范式转换红线 (Paradigm Shift)

旧代码（如 `TMTestHdl.py`、`StatusSeqHdl.py` 等）与新架构有着天壤之别，必须在代码层面进行彻底的破旧立新：

### 从“松散字典拼凑”到“强类型 Dataclass”
- **旧架构**：旧代码中充斥着庞大而松散的 `node = {"static": {}, "dynamic": {}}` 字典构建过程，非常容易出错。
- **新架构**：必须全部废弃字典构建，替换为原生的、强类型的 `ApiNodeData(mode=..., base=..., steps=...)` 结构，并交由 `EngineCtrl` 编译。

### 彻底废除 CmdRouter 与底层越权拦截
- **旧架构**：使用庞大的 `NodeTracker`，并在 `InterceptWsEvent` 中强行越权拦截底层 WebSocket 事件来统计跳闸时长和进度。
- **新架构**：禁止任何此类拦截！底层 `EngineCtrl` 已经屏蔽了 WebSocket 的脏活。你必须重新利用 `BaseApi` 提供的生命周期回调：
  - 用 `onUpdate` 跟踪节点的执行进度，按需发送报告。
  - 用 `onDi` 捕获跳闸变位，实现高精度的动作时间记录。

### 物理值校准与 Factor 参数抹除
- **旧架构**：使用 `self.mgr.PhysToReg(phys_dict, factor=1.0)`。此处的 `factor` 通常用于正负方向的幅值缩放（如反向步进传 `-1.0`）。它**并不**包含隐含的 $\sqrt{2}$（因为前端对于静态、复归、步进本身下发的就是幅度值）。
- **新架构**：新版的 `self.physDictToReg` **不再有 `factor` 参数**！
  - 你在移植时，如果发现旧代码传递了 `factor`，必须在装配物理字典的阶段，**由 Python 原生对所有物理幅度值乘以该比例因子进行缩放/取反**，算清最终的绝对物理值之后，再喂给底层的转换函数！

## 3. 验证测试方案：纯软层面的输出一致性校验

由于新旧架构底层的 FPGA 通信协议已经完全不兼容，**旧代码无法在真实的最新硬件上跑通**。为了验证你的移植是否达到了“逻辑等价”，必须采取以下“纯软件对比”的绝杀方案：

1. **旧代码剥离拦截测试**：编写专门的 Python 测试脚本。利用 Mock 机制拦截旧版 Handler 最终向外输出数据的关卡（可以直接 Mock 替换旧版 `ApiHdlMgr` 的通信层，或者直接拦截它的 `PhysToReg` 返回值）。
2. **模拟 FPGA 推进**：在测试脚本中，向旧代码注入虚假的 WebSocket 确认消息（ACK）和底层 Tick，以此推动旧代码的时序演进，并**打印出旧架构在整个实验流程中预期输出的所有物理量与时序数组**。
3. **新代码同步运行与比对**：用同样的实验配置参数运行你新写的 `BaseApi` 代码。新架构自带完善的日志和物理量反算（通过自动触发的 `calib.RegToPhys`）。
4. **Diff 对比**：将旧代码被拦截打印出的物理数组，与新代码在日志中打印的物理数组进行 Diff 比对。
5. **验收结论**：如果两边在每一毫秒、每一个节点跳转时，计划下发给通道的电压/电流物理幅值完全一致，即可证明“物理初衷”得到了 100% 的精准保留。
